# ドメインルール

## ノードタイプの定義

経路探索システムで使用するノードの種類と役割。

### ノード種別

| タイプ     | 説明                | 特徴                                               |
| ---------- | ------------------- | -------------------------------------------------- |
| `entrance` | 建物入口            | 屋外と屋内をつなぐ接点。`building_id` が設定される |
| `road`     | 道路/廊下上のノード | 屋外では道路、屋内では廊下を表す                   |
| `door`     | 部屋のドア          | 部屋への出入口。`rooms.node_id` から参照される     |

### ノードの属性ルール

- **屋外ノード**: `building_id = NULL`, `floor = NULL`
- **屋内ノード**: `building_id` が設定され、`floor` で階数を管理
- **入口ノード**: `node_type = 'entrance'` かつ `building_id` が設定

### node_id の命名規則

- 小文字英数字とアンダースコアのみ: `^[a-z0-9_]+$`
- 例: `outdoor_node_001`, `building1_floor1_corridor_01`, `entrance_main`

## 経路探索アルゴリズム

### 使用アルゴリズム

- **pgRouting A\*法**: ヒューリスティック探索による最短経路計算
- **時間計算量**: O((V+E)logV)
- **対応グラフ**: 無向グラフ（双方向移動可能）

### 重み計算

エッジごとのコストは距離に検索条件由来の重みを乗じて計算:

```sh
edge_cost  = distance × w_level × w_stairs
total_cost = Σ edge_cost
```

- `distance`: エッジの物理的距離（メートル）
- `w_level`: 道の主要度（level）に応じた重み（検索条件で変動）
- `w_stairs`: 階段の有無に応じた重み（検索条件で変動）

重みはアプリ内で検索条件ごとに定義される（`domain/service/weight.go`）。

### フィルタリングオプション

| オプション   | 説明                   | SQL条件                                           |
| ------------ | ---------------------- | ------------------------------------------------- |
| 階段回避     | 階段を含むエッジを除外 | `has_stairs = FALSE`                              |
| 屋内のみ     | 屋外経路を除外         | `is_indoor = TRUE`                                |
| 屋外のみ     | 屋内経路を除外         | `is_indoor = FALSE`                               |
| 建物指定     | 特定建物内の経路のみ   | `building_id_from = ? AND building_id_target = ?` |
| バリアフリー | バリアフリー経路のみ   | `is_accessible = TRUE`                            |
| 主要度制限   | 指定レベル以下の道のみ | `level <= ?`                                      |

### 近傍点検索

現在地（緯度経度）からもっとも近いノードを検索:

1. PostGISの空間インデックス（GiST）を使用
2. `<->` 演算子で距離順ソート
3. `ST_Distance` で測地線距離を計算

```sql
SELECT id, node_id
FROM nodes
ORDER BY geom <-> ST_SetSRID(ST_MakePoint(lng, lat), 4326)
LIMIT 1;
```

## 屋内外経路の判定ルール

### エッジの屋内外判定

| is_indoor | 説明     | 用途                                     |
| --------- | -------- | ---------------------------------------- |
| TRUE      | 屋内経路 | 建物内の移動（廊下、階段、エレベーター） |
| FALSE     | 屋外経路 | 建物間の移動（歩道、道路）               |

### 建物間移動のルール

1. 屋外から建物へ入る: 屋外ノード → `entrance` ノード
2. 建物内を移動: `is_indoor = TRUE` のエッジを使用
3. 建物から屋外へ出る: `entrance` ノード → 屋外ノード
4. 別の建物へ移動: 屋外経路を経由

### 階数の扱い

- 屋内ノードは `floor` で階数を管理
- 階をまたぐエッジ: `has_stairs = TRUE`（階段）または `has_stairs = FALSE`（エレベーター）
- 階数の範囲: -10 〜 100

## データ整合性の制約

### FK制約を使わない理由

- データ投入の柔軟性（CSV一括投入時の順序制約なし）
- パフォーマンス向上（FK検証のオーバーヘッド削減）
- 静的データのため、アプリケーション層で整合性を保証

### 整合性ルール

#### エッジの整合性

| ルール       | 説明                                                                       |
| ------------ | -------------------------------------------------------------------------- |
| ノード存在   | `node_id_from` と `node_id_target` は `nodes.node_id` に存在する必要がある |
| 自己参照禁止 | `node_id_from != node_id_target`                                           |
| 距離非負     | `distance >= 0`                                                            |

#### 屋内エッジの整合性

| ルール     | 説明                                                               |
| ---------- | ------------------------------------------------------------------ |
| 建物一致   | `is_indoor = TRUE` の場合、両端ノードは同じ `building_id` に属する |
| 建物ID存在 | 両端ノードの `building_id` は `buildings.id` に存在する            |

#### 部屋の整合性

| ルール         | 説明                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 建物存在       | `building_id` は `buildings.id` に存在する必要がある                 |
| ドアノード存在 | `node_id` が設定されている場合、`nodes.node_id` に存在する必要がある |
| ドアノード種別 | 参照するノードの `node_type` は `door` である必要がある              |

#### room_type の値

| タイプ   |
| -------- |
| `講義室` |
| `ゼミ室` |
| `研究室` |
| `卒研室` |
| `実験室` |
| `事務室` |
| `会議室` |

#### 写真の整合性

| ルール     | 説明                                                 |
| ---------- | ---------------------------------------------------- |
| 建物存在   | `building_id` は `buildings.id` に存在する必要がある |
| URL形式    | `url` は `^https?://` で始まる必要がある             |
| 表示順非負 | `display_order >= 0`                                 |

### 整合性チェックのタイミング

- **データ投入後**: 一括インポート完了後に実行
- **定期バッチ**: 日次などで定期実行
- **管理API経由**: 管理者が手動で実行

## 経路の主要度（level）

エッジの道の重要度を表す指標。

| レベル | 説明   | 例                             |
| ------ | ------ | ------------------------------ |
| 1      | 大通り | メインストリート、正門からの道 |
| 2      | 主要道 | 建物間の主要通路               |
| 3      | 一般道 | 通常の通路、廊下               |
| 4      | 脇道   | 裏道、狭い通路                 |
| 5      | 補助道 | 非常口、サービス通路           |

### level パラメータ（検索条件）

検索時の `level` パラメータはハードフィルタではなく、コスト重みの選択に使用。
全レベルの道が経路候補となり、重みによって優先度が変わる。

| level | 意味         | 効果                                         |
| ----- | ------------ | -------------------------------------------- |
| 0     | 距離のみ     | 全経路同価、純粋に最短距離の経路を返す       |
| 1     | 大通り優先   | 脇道のコストが大きくなり、大通りを選びやすい |
| 2     | やや大通り優先 | 大通り寄りだが脇道も許容                   |
| 3     | デフォルト   | バランス型                                   |
| 4     | やや脇道優先 | 大通りのコストが上がり脇道を選びやすい       |
| 5     | 脇道優先     | 大通りのコストが大きくなり、脇道を選びやすい |

重みの定義は `domain/service/weight.go` を参照。

## バリアフリー対応

### is_accessible フラグ

| 値    | 説明                                           |
| ----- | ---------------------------------------------- |
| TRUE  | バリアフリー対応（車椅子通行可、スロープあり） |
| FALSE | バリアフリー非対応                             |

### 階段回避ルール

`has_stairs = FALSE` かつ `is_accessible = TRUE` の経路を優先:

- エレベーター
- スロープ
- 平坦な通路
